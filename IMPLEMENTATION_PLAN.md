# План розвитку KILO·G

Дата: 8 жовтня 2026 року. Основа: поточний проєкт PrintCost, коміт `ded3d89`, Cloudflare Worker `kilo-g`, сайт `web-dev.pp.ua`, Firebase Spark `kilo-g`.

Мета — завершений застосунок для користувачів, менеджерів компаній та адміністраторів: реальні акаунти, захищені права, пропозиції компаній у каталозі, аналітика, податкові оцінки й приватні шаблони розрахунків. Користувач дозволив реалізацію 8 жовтня 2026 року. Кожний функціональний блок завершується перевірками до переходу до наступного.

## Погоджені вимоги

- Три ролі: `user`, `manager`, `admin`. Адміністратор має права на систему; менеджер представляє компанію.
- Адміністратор створює компанію, призначає її менеджерів і змінює ролі зареєстрованих користувачів, зокрема призначає інших адміністраторів.
- Менеджер створює та змінює пластики й пропозиції своєї компанії. Публікація відбувається одразу, без схвалення адміністратором.
- Якщо під час початкової ініціалізації адміністратора немає, першим адміністратором стає власник підтвердженої адреси `web.developer.den@gmail.com`.
- Податкові оцінки: Україна, ФОП 1/2/3 групи та загальна система, опціональний ПДВ, ручне налаштування ставок.
- Користувач має приватні заготовки параметрів для повторних розрахунків.
- У таблиці матеріалів розрахунку для кожного рядка показуються лише особисті матеріали відповідного типу з файлу: для PLA — PLA, для PETG — PETG тощо.
- Платні тарифи не підключаються автоматично. План орієнтується на Workers Free, Firebase Spark та D1 Free.

Початкова модель компаній: одна компанія може мати кількох менеджерів; один менеджер представляє одну компанію. Зміну цього обмеження потрібно зафіксувати до реалізації моделі членства.

## Архітектура і межі доступу

React, TypeScript, Vite й наявний парсер залишаються основою. Firebase Auth підтверджує особу. Firestore зберігає основні дані й перевіряє права; D1 зберігає аналітичні події та агреговані звіти. Уточнення реалізації: bootstrap та адміністративні зміни виконуються атомарними транзакціями наявного Firebase Web SDK і перевіряються Rules. Проміжний Worker для тих самих записів не додає межі довіри, але витрачає додаткову квоту й потребує власних повторів транзакцій. Worker API використовується для аналітики та звітів D1. [Firebase: транзакції](https://firebase.google.com/docs/firestore/manage-data/transactions).

| Компонент | Відповідальність |
| --- | --- |
| Браузер | Інтерфейс, завантаження та локальний аналіз G-code/3MF, розрахунок, формування завантажуваних звітів |
| Firebase Auth | Реєстрація, пароль, підтвердження пошти, відновлення, ID token |
| Firestore Standard | Особисті дані, компанії, пропозиції, реєстр адміністраторів, членство, шаблони, журнал зміни прав |
| Firebase Web SDK + Rules | Атомарні bootstrap, зміна ролей/доступу/компаній та їх журнал; однакова перевірка прямих SDK-запитів |
| Worker `/api/*` | Перевірка запитів, приймання подій, звіти з перевіркою компанії |
| D1 | Обмежені аналітичні події та денні агрегати; доступ лише через Worker |

Статичні сторінки обслуговуються без запуску серверного коду. API маршрутизується окремо, щоб перевищення квоти скрипта не вимикало статичний сайт. Це відповідає [моделі Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/).

Worker отримує Firebase ID token у заголовку авторизації для захищених звітів, перевіряє особу та актуальні права. Основні записи виконує Firebase SDK із Security Rules. Service account ключ у браузері або публічному репозиторії не потрібен. [Firestore REST](https://firebase.google.com/docs/firestore/use-rest-api), [перевірка ID token](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

Основне джерело прав — захищений реєстр адміністраторів і захищене членство в компанії. Поля особистого профілю, `workshopName`, localStorage й дані форми не надають повноважень. Після переходу старий `claims.admin` не залишається альтернативним дозволом. Документна модель підтримується [Firestore Rules](https://firebase.google.com/docs/firestore/solutions/role-based-access).

Без service account Firestore не відрізняє Worker від прямого запиту користувача. Тому всі перевірки ролі, власника, компанії, дозволених полів і незмінних ідентифікаторів повинні працювати також у Rules. Обмеження швидкості тільки на Worker не захистить прямі Firestore-запити.

| Дія | Користувач | Менеджер | Адміністратор |
| --- | --- | --- | --- |
| Каталог і пошук | Так | Так | Так |
| Особисті матеріали, принтери, історія, шаблони | Власні | Власні | Власні |
| Створення та редагування пропозицій компанії | Ні | Своєї активної компанії | Будь-якої компанії |
| Сховати власну пропозицію / змінити наявність | Ні | Так | Так |
| Створення компаній, призначення менеджерів | Ні | Ні | Так |
| Зміна глобальних ролей і блокування доступу | Ні | Ні | Так, із захистом останнього адміністратора |
| Виробники, типи пластику, температурні довідники | Читання | Читання; вибір для власного товару | Редагування |
| Аналітика | Без адміністративних звітів | Агрегати своєї компанії | Агрегати системи й компаній |
| Приватні обчислення інших користувачів | Ні | Ні | Ні; керування каталогом не надає цього доступу |

Демо залишається окремим локальним прикладом, без адміністративних і менеджерських операцій та без запису подій у робочу аналітику.

## Модель даних і життєвий цикл

| Шлях / сутність | Призначення й обмеження |
| --- | --- |
| `users/{uid}` і наявні підколекції | Приватний профіль, принтери, матеріали, налаштування та історія власника |
| `userDirectory/{uid}` | Мінімальні дані зареєстрованого акаунта для пошуку адміністратором; без фінансової історії. Адміністратори мають окремо обґрунтований доступ до цього службового списку |
| `system/authorization` | Обмежений список UID активних незаблокованих адміністраторів, початковий власник, дата ініціалізації, версія; після створення не можна видалити або залишити без адміністратора |
| `accountAccess/{uid}` | Стан доступу до застосунку; користувач не змінює власне блокування або службові параметри |
| `memberships/{uid}` | Компанія менеджера, активність, автор і дата призначення; змінює адміністратор |
| `companies/{companyId}` | Публічні реквізити, сайт, дозволені домени посилань, активність; приватні службові контакти зберігати окремо |
| `companyOffers/{offerId}` | Пластик/варіант компанії: бренд, тип, колір, вага, діаметр, ціна, валюта, наявність, URL, статус, автор і дати. `companyId` та автор створення незмінні |
| `users/{uid}/calculationTemplates/{id}` | Приватна назва й параметри майбутнього розрахунку; без завантажених моделей і готових результатів |
| `accessAudit/{eventId}` | Незмінний журнал: хто, кому й які права/прив’язки змінив, серверний час |
| D1 `events`, `daily_metrics` | Події з обмеженими полями й денні агрегати; без email, IP та приватної історії розрахунків |

Пластик менеджера може бути новою позицією його компанії або пропозицією для наявного товару. Власні назва, параметри варіанта та магазин зберігаються в документі компанії. Якщо виробника чи типу ще немає у довіднику, менеджер задає обмежену валідовану назву у власній пропозиції та публікує її одразу. Адміністратор вирішує лише питання додавання до спільного довідника; це не блокує власну позицію компанії. Менеджер не переписує загальний довідник і не надає своїй позиції адміністративну позначку перевірки.

Після реєстрації та підтвердження пошти людина має роль користувача. Адміністратор знаходить її в службовому списку, створює компанію або вибирає наявну та призначає менеджером. Адміністратор не задає людині пароль. Менеджер бачить кабінет своєї компанії й одразу публікує коректні пропозиції. Адміністратор може приховати пропозицію або вимкнути компанію; менеджер не відновлює адміністративно заблокований товар.

Для одночасного редагування використовувати версію запису або транзакцію й явне повідомлення про конфлікт. Перевіряти типи, ціну, межі текстів, URL, посилання на довідники та дозволені переходи статусу на створенні й оновленні. Компанія визначається через поточне членство, а не довільне поле запиту.

## Безпечний перший адміністратор

1. Перед переходом перевірити наявні server-issued admin claims. Якщо адміністратори вже є, перенести їх у реєстр; відсутність нового документа ще не означає відсутність старих прав. Ця перевірка й перенесення завершуються до ввімкнення нових правил bootstrap.
2. Для справді порожньої системи дозволити одноразову атомарну ініціалізацію лише токену з точною підтвердженою адресою `web.developer.den@gmail.com`.
3. Адресу та підтвердження перевіряти за довіреними даними Firebase, без довіри до форми або редагованого профілю.
4. Реєстр створюється з перевіркою його відсутності. Повторні й паралельні спроби не перепризначають власника. Правила відхиляють bootstrap також при прямому SDK-запиті іншого користувача.
5. Зміни ролей, членства та блокування й відповідний перевірений журнал виконуються атомарно, також при прямих SDK-запитах. Блокування адміністратора в тій самій транзакції прибирає його UID із реєстру; Rules перевіряють узгоджений стан після транзакції. Порожній реєстр заборонений, зокрема при двох паралельних блокуваннях/пониженнях ролі.
6. Після призначення права оновлюються в UI; наступна захищена операція перевіряє актуальний реєстр. Окремо описати відновлення доступу при втраті акаунта, не відкриваючи автоматичне захоплення системи.

## Аналітика каталогу

Початкові події: пошук і застосування фільтрів, пошук без результату, фактичний показ пропозиції на екрані, відкриття деталей, перехід на сайт продавця, додавання товару до особистих матеріалів. CTR обчислюється як переходи / виміряні покази однієї пропозиції за той самий період.

Менеджер бачить покази, кліки, CTR, популярні власні позиції, динаміку за днями, фільтри й категорії, що приводять до його пропозицій. Адміністратор бачить загальні показники, пошуки без результату, активність компаній та стан квот. Дати звітів узгоджуються з часовим поясом Europe/Kyiv; межі серверних квот визначаються правилами відповідної платформи.

Пропозиція й компанія для події визначаються через довірені дані каталогу. Повторні `eventId` не збільшують підсумки; вводяться обмеження розміру пакета, кількості подій, дозволених типів і швидкості. Демо й тести виключаються. Події не містять email, IP, даних файлів чи повного довільного пошукового тексту: для пошуку зберігаються безпечні категорії/ключові слова з каталогу, фільтри й кількість результатів. Додати пояснення збору аналітики й керування ним у політиці приватності.

Пропонований початковий бюджет: до 5 000 детальних подій на день, збереження деталізації 30 днів і денних агрегатів 12 місяців. Це налаштування застосунку; остаточні межі перевіряються за фактичним розміром таблиць та кількістю записаних рядків. Індекси, агрегати й очищення теж витрачають квоту D1. Локальний rate limit не вважається точним глобальним лічильником.

Помилка або вичерпання аналітики не блокують розрахунок, збереження особистих даних чи звичайний перехід до продавця. Аналітика показує виміряну активність, а не підтверджені покупки: сторонній магазин не передає продажі, частину подій можуть втрачати мережа й блокувальники, а частину створювати боти.

## Відповідність матеріалів типу з файлу

У секції «Матеріали та філаменти замовлення» список формується окремо для кожного філамента кожної пластини. Джерело — особистий каталог користувача; архівні матеріали не показуються. Для рядка PLA не можна вибрати PETG, ABS, ASA, TPU або PLA-CF. Нульовий залишок позначається, як і зараз; сам по собі він не змінює тип матеріалу.

- Зіставлення використовує поле типу матеріалу, а не назву товару, бренд чи колір. Регістр і крайні пробіли нормалізуються. PLA-CF не прирівнюється до PLA за початком назви; інші варіанти об’єднуються лише за явним правилом довідника. Наприклад, наявний `eSUN PLA+ White` має тип `PLA` і залишається в списку для PLA.
- Одна перевірка відповідності застосовується у списку, обробнику вибору, автоматичному підборі, збереженні/застосуванні відповідності, перенесенні вибору з каталогу та застосуванні шаблону. При перенесенні матеріалу його ID, назва й ціна мають стосуватися одного матеріалу. Якщо позицію ще не додано до особистого каталогу, перенесення ціни не вигадує особистий ID і не залишає ID іншої котушки.
- Видалена, архівна або несумісна з поточним типом збережена відповідність не підставляється в новий розрахунок. Інтерфейс пояснює необхідність повторного вибору; у рядку не залишається прихованого вибраного матеріалу, якого немає у списку.
- Якщо відповідних матеріалів немає, показати повідомлення та дію додавання матеріалу з попередньо заповненим типом. Зберегти можливість явно вказати ціну вручну без вибору матеріалу; не підставляти довільну котушку чи вигадану ціну.
- Якщо тип не визначений у файлі, зокрема парсер повертає `Невідомий`, користувач явно уточнює його перед вибором матеріалу. Не показувати всі пластики як відповідні й не вгадувати тип за кольором. Зміна уточненого типу повторно перевіряє поточний вибір; повідомлення парсера пояснює цей порядок.
- Зміна особистого каталогу повторно перевіряє відповідності в поточному незбереженому розрахунку. Старі збережені snapshots залишаються незмінними; при створенні нового розрахунку з історії відповідність перевіряється знову.

Місця реалізації: `FilamentMappingTable`, `CalculatorPage`, `AppDataContext` (`findBestMaterialMatch`, `saveFilamentMapping`), повідомлення `printFileParser`, застосування шаблонів і предметні тести зіставлення.

## Податки та ПДВ

Податковий блок опціональний. Без нього результат має збігатися з поточним калькулятором. Пресет має дату дії, версію, джерело й можливість вручну скоригувати значення.

| Режим | Модель оцінки |
| --- | --- |
| ФОП 1/2 групи | Фіксовані місячні платежі розподіляються користувачем на замовлення або години; група не підтверджує дозволеність конкретної діяльності |
| ФОП 3 групи | Єдиний податок і військовий збір від відповідного доходу; коректне поєднання режиму й ПДВ |
| Загальна система ФОП | Окрема оцінка чистого оподатковуваного доходу з явно вказаними документальними витратами; виробнича собівартість не підставляється автоматично |
| Ручний режим | Явні база, ставки й фіксовані платежі з поясненням припущень |

ЄП, військовий збір, ПДФО, виділена частка ЄСВ та інших місячних платежів показуються окремо. Пільги й звільнення користувач задає явно; застосунок не визначає їх із назви принтера чи товару. Для різних режимів потрібні різні бази й методи розподілу. [ДПС: спрощена система у 2026 році](https://sumy.tax.gov.ua/media-ark/news-ark/print-975635.html), [ДПС: загальна система й платежі у 2026 році](https://mk.tax.gov.ua/media-ark/news-ark/976670.html).

ПДВ показується як база без ПДВ, сума ПДВ та остаточна ціна. Підтримати позначення ціни матеріалу з ПДВ/без ПДВ. Невідшкодовуваний вхідний ПДВ залишається у витратах; його виключення потребує явної підстави, а не тільки перемикача статусу платника. ПДВ продажу розраховується окремо. Суму ПДВ продажу не називати платежем до бюджету без окремого обліку податкового кредиту. [ПКУ: ПДВ](https://www.tax.gov.ua/nk/rozdil-v--podatok-na-dodanu-vartist/), [ПКУ: єдиний податок](https://tax.gov.ua/nk/rozdil-xiv--spetsialni-podat/edynyi-podatok).

Інтерфейс має два зрозумілі сценарії: оцінити податки для вказаної ціни або підібрати ціну, яка покриває податки й бажаний прибуток. Цільова маржа в податковому режимі — прибуток після врахованих податків, поділений на виручку без ПДВ. Податок від виручки не компенсується простим додаванням такого самого відсотка до собівартості. Мінімум і округлення застосовуються до кінцевої ціни, після чого податкові суми та прибуток перераховуються. Неможлива маржа або відсутня необхідна база дає неповний результат із поясненням.

У підсумку: виробнича собівартість, враховані податки/платежі, ціна без ПДВ, ПДВ, ціна клієнту, прибуток до й після врахованих податків. Така оцінка допомагає встановити ціну замовлення; декларація й повний бухгалтерський облік до цього обсягу не входять.

## Шаблони й незмінність історії

Шаблон містить назву, принтер, тариф, додаткові витрати, резерв, націнку/маржу, мінімум, округлення, податкові параметри та за потреби відповідності матеріалів. Дії: створити з поточного налаштування, застосувати, перейменувати, дублювати, змінити, видалити; можна вибрати шаблон за замовчуванням.

Застосування копіює параметри в новий розрахунок. Шаблон не підміняє реальні масу, час, пластини або типи філаментів завантаженого файлу. Видалений принтер, видалений/архівний або несумісний за типом матеріал вимагає повторного вибору. Зміни шаблону або ставок не змінюють історію: snapshot зберігає параметри й результати на момент розрахунку, версію алгоритму та податкового пресета. Перерахунок створює новий запис із посиланням на попередній. Редагування історії дозволяє лише описові поля; суми й вхідні параметри захищені правилами.

## Порядок робіт і завдання

Кожний етап завершується предметними перевірками та переглядом його критеріїв приймання. Етапи 4 і 5 можна виконувати паралельно після стабілізації моделі даних.

| Етап | Завдання | Результат / умова завершення |
| --- | --- | --- |
| 1. Архітектура й середовище | Зафіксувати схему, права, контракти, обмеження; окрема гілка `codex/…`; Firebase емулятори й локальний D1; перевірити CPU токенів/звітів і безкоштовні квоти | Підтверджений спосіб роботи API на Free, незалежні тестові дані, погоджені інваріанти |

| 3. Компанії й каталоги | Адмінський список акаунтів/компаній/ролей; кабінет менеджера; власні пластики й URL; миттєва публікація; статуси, конфлікти, пагінація, індекси й кеш | Менеджер A не змінює компанію B; каталог показує коректні компанію, ціну, вагу та посилання |

Зіставлення, шаблони й історія | Фільтрація матеріалів за типом кожного рядка; перевірка вибору й збережених відповідностей; стани відсутнього/невідомого типу; приватний repository і UI шаблонів; застосування копій; захист input/result; версії snapshots; пагінація історії | Список і всі способи підстановки узгоджені за типом; шаблон працює після повторного входу; його зміна не змінює старий розрахунок |

Міграція й експлуатація | Локальний захищений експорт перед міграцією, dry-run, перенесення наявних прав/каталогу, збереження ID та вподобань; експорт і видалення власних даних, журнал, помилки, документація | Повторний запуск міграції не дублює дані; протестований відкат; старі особисті записи читаються; видалення акаунта не залишає активних повноважень |

Перед міграцією адміністративно підтвердити, кому належать наявні магазини. Збіг назви магазину з назвою компанії не передає власність. Початковий каталог зберігається; непідтверджені старі записи залишаються під контролем адміністратора. Нові податкові поля необов’язкові для старих документів; масове переписування особистої історії не потрібне.

Видалення власного акаунта потребує недавньої аутентифікації, відкликання прав і повторно виконуваного очищення приватних даних. Пропозиції компанії належать компанії та не зникають при звільненні менеджера. Для останнього адміністратора потрібне попереднє призначення іншого. Видалення акаунта напряму в Firebase Console обходить політику застосунку; на цей випадок має бути окрема процедура відновлення реєстру власником проєкту.

## Сценарії приймання

- [ ] Реєстрація → лист → підтвердження → налаштування → розрахунок → збереження → повторний вхід → та сама історія.
- [ ] Невірний пароль, прострочене/повторне посилання, повторний email і збій мережі мають зрозумілі стани; відновлення не розкриває зайвих даних про акаунт.
- [ ] Непідтверджена чи інша пошта не отримує bootstrap; дві одночасні спроби не перепризначають адміністратора.
- [ ] Підтверджена адреса `web.developer.den@gmail.com` автоматично отримує роль у справді порожній системі; наявний перенесений адміністратор закриває bootstrap.
- [ ] Адміністратор призначає та відкликає адміністратора/менеджера; останнього активного адміністратора не можна заблокувати або позбавити ролі.
- [ ] Два адміністратори при паралельному блокуванні/пониженні ролей не залишають систему без активного адміністратора; прямий запис `accountAccess` не обходить інваріант реєстру.
- [ ] Редагування профілю/localStorage, старий claim або прямий SDK-запит не обходять нові права.
- [x] Менеджери двох компаній не читають службові дані та не змінюють пропозиції одне одного; відкликання прав блокує наступний запис.
- [x] Новий пластик менеджера публікується без схвалення; ціна, упаковка, колір і URL валідні; адміністративне блокування не обходиться.
- [x] Невідомі довіднику виробник/тип не затримують публікацію власної валідної позиції; спільні довідники й позначки перевірки залишаються адміністративними.
- [ ] Користувач, менеджер і адміністратор не читають чужі приватні розрахунки й шаблони.
- [ ] Демо не має менеджерських/адмінських маршрутів і не надсилає робочі події.
- [ ] Для рядка PLA список містить лише активні особисті матеріали типу PLA; PETG, ABS, ASA, TPU і PLA-CF відсутні. У файлі з кількома типами та пластинами кожний рядок має свій правильний список; регістр і крайні пробіли не порушують зіставлення.
- [ ] Несумісні, архівні й видалені матеріали не підставляються через стару відповідність, шаблон, перенесення з каталогу чи обробник вибору; ID, назва й ціна перенесеного матеріалу узгоджені.
- [ ] За відсутності відповідного матеріалу можна додати його з потрібним типом або явно вказати ціну вручну; невизначений тип потребує уточнення; нульовий залишок позначений; зміна типу чи каталогу не залишає прихованого несумісного вибору.
- [x] Податки вимкнені — старі арифметичні результати незмінні; фіксовані платежі не множаться помилково на кожну пластину.
- [x] Контрольний приклад для оцінки ціни: собівартість 1000 грн, націнка 20%, податки від виручки 3% + 1%, ПДВ 20%, без інших платежів та округлення → база 1250 грн, податки 50 грн, ПДВ 250 грн, клієнту 1500 грн, прибуток після врахованих податків 200 грн. Це арифметична фікстура, а не універсальна податкова модель.
- [x] Суми з ПДВ/без ПДВ узгоджені; на загальній системі використовується явно визначена податкова база; невідома база не дає вигаданої суми.
- [x] Для загальної системи з явно заданою базою 500 грн і ставками ПДФО 18% та ВЗ 5% оцінки — 90 і 25 грн; нульова/від’ємна база не створює від’ємний податок або вигадане відшкодування, фіксовані платежі перевіряються окремо.
- [x] Несумісні пресети ФОП 3 групи 5% + ПДВ або 3% без статусу платника відхиляються; прибуток/маржа використовують виручку без ПДВ, невідшкодовуваний вхідний ПДВ не зникає з витрат.
- [ ] Зміна ставок/шаблону/принтера не переписує snapshot; пряме оновлення input/result відхиляється; перерахунок створює новий запис.
- [ ] Повторні події не збільшують метрики; підроблений companyId не відкриває звіт; клік не трактується як покупка.
- [ ] Квота/збій D1 не блокують калькулятор і перехід до продавця; ліміти запитів та очищення залишають запас на звіти.
- [ ] Історія понад 200 записів і каталог понад поточний ліміт доступні через пагінацію; фільтри відповідають індексам і Rules.
- [ ] Старі користувачі, вподобання та каталог переживають міграцію; повторний запуск і відкат перевірені на тестових даних.
- [ ] Експорт/видалення приватних даних ізольовані за UID; очищення акаунта можна безпечно повторити після збою; пропозиції компанії та права інших менеджерів збережені.
- [ ] Прямі URL, мобільна навігація, клавіатура й повідомлення про помилки працюють для всіх ролей.
- [ ] Новий API виміряний на Workers Free для холодного/прогрітого ключа, неправильного/простроченого токена, пакетів подій і звітів; є запас до межі CPU.

## Безкоштовні межі та умови запуску

Квоти перевірені за документацією 8 жовтня 2026 року; перед деплоєм їх треба звірити з фактичним тарифом і поточними умовами акаунтів.

| Сервіс | Межі, важливі для плану |
| --- | --- |
| Workers Free | 100 000 викликів скрипта на день, 10 мс CPU на HTTP-запит |
| Firestore | 1 GiB, 50 000 читань і 20 000 записів на день; вихідний трафік 10 GiB на місяць |
| D1 Free | 5 млн прочитаних і 100 000 записаних рядків на день; одна база до 500 MB |
| Firebase Auth Spark | Листи підтвердження — 1000/день, відновлення пароля — 150/день |

Джерела: [Workers](https://developers.cloudflare.com/workers/platform/limits/), [Firestore](https://firebase.google.com/docs/firestore/quotas), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [Auth](https://firebase.google.com/docs/auth/limits).

На Free потрібні вимірювання CPU: Cloudflare зазначає, що складніші запити з аутентифікацією можуть потребувати 10–20 мс. Кешувати публічні ключі та обмежити обсяг запитів/звітів. Якщо локальна JWT-перевірка не вкладається, перевірити делегування аутентифікації захищеному Firestore REST-запиту від імені користувача, із тестами підроблених токенів і чужого UID та врахуванням додаткових читань. Платний тариф не вмикається як прихований спосіб пройти цей критерій.

Firebase Functions і Cloud Storage не включаються в цей Spark-план. Файли друку обробляються локально, шаблони — обмежені документи, звіти завантажуються з браузера.
