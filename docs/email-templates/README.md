## Що можна застосувати у Firebase Console

У [Authentication → Templates](https://console.firebase.google.com/project/kilo-g/authentication/emails) для кожного типу можна налаштувати ім'я й адресу відправника, Reply-to і тему. **Тіло листа консоль дозволяє змінювати лише для відновлення пароля.** Отже, HTML підтвердження й зміни адреси не можна обіцяти просто вставити в стандартні шаблони. Це обмеження редактора, а не привід переходити на платний тариф. [Офіційні поля й обмеження](https://support.google.com/firebase/answer/7000714).

Підготовлені значення для ручного застосування:

| Поле | Значення |
| --- | --- |
| Template language | Ukrainian |
| Public-facing name у налаштуваннях проєкту | `KILO·G` |
| Sender name | `KILO·G` |
| Sender local part | `noreply` |
| Sender domain після перевірки | `web-dev.pp.ua` |
| Бажана повна адреса From | `noreply@web-dev.pp.ua` |
| Reply-to | Залишити порожнім або вказати реальну скриньку, яку власник читає |
| Subject | Тема відповідного листа з таблиці вище |
| Password reset → Message | Вміст `reset-password.txt` зі збереженим `%LINK%` |

Для найближчого налаштування через консоль підходить текстова версія відновлення. HTML цього листа можна пробувати лише якщо редактор зберігає HTML; після збереження треба отримати справжній тестовий лист і перевірити результат. Збереження всіх стилів стандартним редактором тут не підтверджене.

Для повністю власної HTML-верстки всіх листів офіційний шлях — генерувати action links на сервері через Firebase Admin SDK і надсилати їх своїм поштовим сервісом/SMTP. Ці файли готові як дизайн для такого підключення, але інтеграція й провайдер **не створені**. Саме налаштування custom SMTP не знімає обмеження редактора тіла листа. Вартість та ліміти обраного сервісу треба перевірити перед підключенням; безкоштовність довільного обсягу не гарантована. [Генерація email action links](https://firebase.google.com/docs/auth/admin/email-action-links).

## Власна адреса noreply@web-dev.pp.ua

Так, Firebase підтримує домен відправника. У повідомленні користувача було `web-dev.pp.u`; тут використано домен чинного сайту **`web-dev.pp.ua`**. Поштова скринька не є кроком перевірки домену в Firebase; якщо потрібно отримувати відповіді, для Reply-to потрібна робоча скринька або пересилання.

Порядок майбутнього налаштування:

1. Увійти власником проєкту `kilo-g`, відкрити потрібний шаблон і натиснути олівець → **Customize domain**.
2. Вказати `web-dev.pp.ua`. Скопіювати **саме ті TXT/CNAME**, які Firebase згенерує для цього проєкту.
3. Додати їх у Cloudflare DNS, перевіривши наявні поштові записи. CNAME для перевірки/поштової автентифікації встановити в **DNS only**, без проксі. SPF має бути один: якщо `v=spf1` уже є, об'єднати дозволені джерела замість другого SPF-запису. Не замінювати чинні MX. [Перевірка CNAME у Cloudflare](https://developers.cloudflare.com/dns/manage-dns-records/troubleshooting/cname-domain-verification/).
4. Дочекатися **Verification complete** (за документацією перевірка може зайняти до 24 годин), натиснути **Apply Custom Domain**, перевірити результат для кожного шаблона. Вказати `noreply` і Sender name `KILO·G`.
5. Отримати листи підтвердження та відновлення на контрольну скриньку. Перевірити From, тему, SPF/DKIM у заголовках та посилання.

DNS-значення тут навмисно не вигадані. Для зміни From через стандартну доставку Firebase окремий SMTP не є кроком описаного Google процесу. Поточні DNS, наявність скриньки й реальну доставку ще не перевіряли. [Офіційне налаштування custom domain](https://firebase.google.com/docs/auth/email-custom-domain?hl=en).

## Посилання й безпечне підключення

- `%LINK%` — повне **унікальне** action link, отримане від Firebase для відповідного користувача й операції. Не замінювати його просто на `/auth/login`, статичне `/auth/callback` чи посилання зі скриншота. У HTML воно використане і в кнопці, і в резервному посиланні.
- `%EMAIL%` — адреса отримувача; `%NEW_EMAIL%` — нова адреса тільки в листі зміни. При власному надсиланні ці маркери замінює сервер: Firebase Admin SDK автоматично HTML-файли не обробляє.
- Під час майбутньої серверної підстановки екранувати текст і HTML-атрибути, для посилання дозволяти тільки HTTPS URL від налаштованого Firebase handler. Не вставляти неперевірені дані як HTML.
- Не записувати action links / `oobCode`, паролі, SMTP credentials чи service-account key у Git, аналітику та логи. Власне надсилання потребуватиме захисту від зловживань і повторних запитів; цей пакет його не додає.
- Підготовлений `https://web-dev.pp.ua/auth/callback` підтримує `verifyEmail`, `resetPassword` і `recoverEmail` (повернення попередньої адреси). Код перевіряється через Firebase перед застосуванням і має відповідати режиму посилання. Після recovery користувач може перейти до відновлення пароля; лист не надсилається автоматично. MFA й `verifyAndChangeEmail` не ввімкнені в застосунку та callback їх відхиляє. Поки цей код не опублікований, зберігайте штатний Firebase handler; перед зміною спільної action URL перевірте всі три режими на опублікованій версії.
- Custom sender domain і `VITE_FIREBASE_AUTH_DOMAIN` — різні налаштування. Не змінювати OAuth authDomain або Firebase Hosting/DNS сайту лише заради адреси From. Після застосування домену перевірити фактичні action links: для адреси handler потрібне окреме коректне налаштування.

## Перевірка цього пакета

Перевірено локальний перегляд на звичайній ширині браузера та **320 px**: усі три листи без горизонтальної прокрутки. Окремі fixture-листи з адресою довжиною 208 символів і action links довжиною 322–324 символи також не виходять за ширину. Перевірка структури трьох HTML/текстових пар пройшла: маркери узгоджені, кнопка й резервне посилання використовують один `%LINK%`, усі таблиці мають `role="presentation"`, активного контенту та зовнішніх ресурсів немає. Докази й helper для цієї перевірки збережені в ігнорованому `output/email-template-proof/` та `output/email-template-check.mjs`; справжніх кодів у них немає.

Нових залежностей, маршрутів, поштових запитів чи production writes цей пакет не додає. Справжні Gmail/Outlook/Apple Mail, доставка, dark-mode перефарбування поштовим клієнтом та збереження HTML у Firebase потребують окремого приймання після підключення. За відключених стилів зміст і текстові посилання мають залишатися доступними; `.txt` можна надсилати як plain-text частину multipart/alternative.
