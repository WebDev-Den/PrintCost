# REST API імпорту KILO·G

**API працює у production з 9 жовтня 2026.** Queue `kilog-imports`, міграції D1 0002/0003 та окремий сервісний акаунт Firebase активовані. Зовнішній API-ключ і живий кабінет пройшли контрольні імпорти 1/1 та 2/2; upsert, company JSON, збереження опису, профіль PLA й idempotency перевірені. Чинний реліз і незавершене приймання — [REMAINING_TASKS.md](./REMAINING_TASKS.md).

## API для зовнішнього програмного забезпечення

Базова адреса: https://web-dev.pp.ua/api/v1. Використовуйте HTTPS. Вкладка **API та імпорт** доступна лише активним admin/manager із підтвердженою поштою.

У блоці **Імпорт JSON** натисніть **Завантажити зразок JSON**: браузер збереже `kilog-import-example.json` у чинному зовнішньому форматі API. Замініть приклад товару та `productUrl` своїми даними; менеджер використовує лише дозволені домени своєї компанії. Готовий файл можна обрати на цій же сторінці або передати зовнішньому ПЗ. Завантаження зразка не запускає імпорт, не змінює текст у формі, не містить API-ключа і не витрачає серверних квот.

Створіть власний ключ у кабінеті, підтвердивши поточний вхід. Він діє 90 днів, показується один раз, у D1 зберігається лише SHA-256. Зберігайте plaintext у захищених налаштуваннях свого ПЗ; не додавайте до URL, JSON, Git або логів. Ротація/відкликання негайно забороняє старий ключ і скасовує незавершену частину імпортів. Уже почата порція до 5 записів може завершитися. Після зміни ролі/компанії, блокування/розблокування або відкликання Firebase сесій потрібен новий ключ.

Для акаунта з прив’язаним Google створення, оновлення та відкликання ключа за замовчуванням підтверджуються повторним Google-входом; пароль сайту не потрібний. Виберіть той самий Google-акаунт. Якщо також прив’язаний email/password, можна обрати підтвердження паролем облікового запису. Для акаунта лише з email/password потрібний його поточний пароль. Скасування, заблоковане вікно чи інший Google-акаунт не змінюють ключа.

| Метод і шлях | Результат |
|---|---|
| POST /imports | Прийняття JSON у чергу; 202, id, statusUrl. Результат перевірки записів — у стані імпорту |
| GET /imports | Останні 30 імпортів; менеджер лише власні, admin усі |
| GET /imports/{id} | Стан, лічильники, помилки та результат кожного запису |
| DELETE /imports/{id} | Прибрати завершений імпорт з історії; товари каталогу збережені |
| DELETE /imports | JSON `{"ids":["UUID"]}`: до 30 унікальних ID, до 4 KiB; `deletedIds` і `unavailableIds` |
| GET /api-key | Метадані власного ключа; лише Firebase сесія кабінету |
| POST /api-key | Створення/ротація власного ключа; свіжий Firebase вхід до 5 хвилин |
| DELETE /api-key | Відкликання власного ключа; свіжий Firebase вхід |

У зовнішніх запитах: `Authorization: Bearer <ключ>`. POST також потребує `Content-Type: application/json` та `Idempotency-Key` (1–128 латинських букв/цифр, дефіс чи підкреслення).

Кабінет використовує Firebase ID token і `X-Firebase-AppCheck`; обидва додаються клієнтом автоматично. Права читаються свіжо через Firestore Rules під точною перевіреною сесією, без переходу на сервісні credentials при відмові. Зовнішній API-ключ не потребує браузерного App Check: сервер окремо перевіряє чинний Firebase-акаунт, роль і дозволені компанії. Не використовуйте браузерний ID token як постійний ключ свого ПЗ.

Для повтору того самого запиту після мережевого збою використовуйте той самий Idempotency-Key і незмінний вміст JSON, включно з пробілами та порядком полів. Змінений вміст з тим самим ключем отримує 409. Для наступного оновлення використовуйте новий ID. Ідемпотентність діє протягом зберігання історії, 30 днів. Раніше прийняті імпорти з нормалізованим JSON зберігають попереднє порівняння нормалізованого вмісту.

**202 означає прийняття до черги.** HTTP-запит перевіряє коректність JSON-об’єкта, дозволені верхні поля `companies`/`offers`, масиви, розмір і загальну кількість записів; створення компаній менеджером одразу повертає 403. Черга перевіряє всі поля, URL, ціни й дублікати всього JSON до першого запису у Firestore. Якщо дані некоректні, імпорт переходить у `failed`, `GET /imports/{id}` повертає `error: "HTTP_422: …"`, а жодна позиція не записується. Така помилка не повторюється автоматично, але прийнятий імпорт витрачає інтервал і денну квоту. Виправте JSON і після дозволеного інтервалу надішліть його з новим Idempotency-Key.

```json
{
  "offers": [{
    "externalId": "pla-white-1000",
    "name": "PLA White 1 kg",
    "brand": "Example",
    "type": "PLA",
    "colorName": "Білий",
    "colorHex": "#ffffff",
    "spoolWeightGrams": 1000,
    "priceUah": 600,
    "productUrl": "https://shop.example.com/pla-white",
    "inStock": true
  }]
}
```

Усі поля прикладу обов’язкові. `externalId` — сталий ID із вашої системи, 1–160 символів: повтор оновлює той самий документ у межах компанії. ID між компаніями незалежні. API не видаляє позиції, яких немає у JSON. Вручну створені позиції та API-позиції мають різні IDs, автоматичного злиття за назвою немає.

`priceUah` — ціна всієї упаковки, до двох знаків після коми; `spoolWeightGrams` — вага упаковки в грамах. Ціна за кг рахується каталогом. Необов’язкові поля: companyId, family, colorTone, packagingType (spool/refill), diameterMm, description, status (published/hidden/blocked; blocked лише admin). На створенні: spool, 1.75 мм, порожній description, special. Пропущені description/packagingType/diameterMm/colorTone на оновленні зберігаються.

**Кожний імпорт створює або повертає пропозиції в чернетки (`hidden`).** Навіть `status: "published"` у JSON не публікує товар: поле приймається для сумісності зі старим ПЗ, але сервер ставить чернетку. Раніше опубліковані товари після оновлення також потребують повторної публікації. Адміністраторське блокування зберігається; менеджер не може оновлювати заблоковану пропозицію. Admin може передати `status: "blocked"`, але імпорт не знімає вже наявного блокування. Чернетки не відображаються у відкритому каталозі.

Після імпорту відкрийте **Адмінку каталогу**, оберіть потрібні чернетки та натисніть **Опублікувати обрані** для масової активації до 100 завантажених записів. Адміністратор також обирає компанію; менеджер бачить лише свою. Менеджер може створювати, редагувати, видаляти та публікувати лише пропозиції своєї активної компанії; адміністратор керує всіма компаніями. Для зняття блокування використовуйте адмінку, а не JSON. Видалення потребує підтвердження; повторний імпорт того самого externalId може створити товар знову як чернетку.

Тип нормалізується до великих літер; профіль підбирається з актуальних temperatureProfiles або стандартних PLA/PETG/ABS/ASA/TPU/PA/PLA-CF/PC. Температури не дублюються у пропозиції: каталог застосовує актуальний профіль. Без профілю потрібна явна family: Стандартні / Інженерні / Гнучкі / Композитні / Підтримки. Видалений адміністратором профіль не відновлюється імпортом.

Менеджер працює лише зі своєю призначеною активною компанією та точними allowedDomains. WWW, інші піддомени, IP, HTTP, порт і URL із user/password не отримують автоматичного дозволу. Адміністратор може додавати домени у компанії.

Адміністратор також передає `companies` перед обробкою offers:

```json
{"companies":[{"name":"Магазин пластику","website":"https://shop.example.com/","allowedDomains":["shop.example.com"],"status":"active"}]}
```

Компанія визначається за companyId або точним доменом URL. Якщо admin companyId не знайдений, виконується пошук за доменом. Якщо компанії немає — створюється активна компанія з назвою домену, website=https://домен/, allowedDomains=[домен]. Admin доповнює її у «Користувачі та компанії». Менеджер не може створювати компанії чи автоматично отримувати права на домен. Для неоднозначного домену потрібен companyId. Сервер не відвідує сайти і не збирає з них дані.

```sh
curl -X POST "https://web-dev.pp.ua/api/v1/imports" \
  -H "Authorization: Bearer $KILOG_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: batch-2026-10-09-001" \
  --data-binary @offers.json
```

## Ліміти і відновлення

- 100 записів сумарно companies+offers та 32 КіБ UTF-8 за запит; один активний імпорт на користувача. Більші файли розділіть на менші порції, кожна з власним Idempotency-Key та дотриманням інтервалу. Пробіли й описи також входять до розміру. Раніше прийняті завдання більшого розміру черга завершує, але новий POST понад 32 КіБ отримує 413, включно з повтором старого великого запиту.
- Manager — раз на 3600 секунд; admin — раз на 300 секунд. Ротація ключа не скидає інтервал.
- Спільно за UTC-добу: 2000 записів, 100 імпортів, 500 відправлень імпортної черги та 300 службових повідомлень. Сумарні 2000 записів, розділені на максимум 100 імпортів, потребують не більше 480 звичайних повідомлень із порціями по 5; залишається щонайменше 20 відправлень для відновлення. Бюджет успішної перевірки прав розділений: 500 запитів менеджерів і незалежний резерв 500 запитів адміністраторів.
- До читання Firebase діють 30 HTTP-запитів/хвилину/IP та UID, атомарні спільні попередні резерви: 500 для відомих ключів адміністратора, 500 менеджера та 100 для UID без чинного ключа. Відхилені спроби теж витрачають попередній резерв. Персональні межі: 10 для невідомого UID, 200 для менеджера та 500 для адміністратора. Коли спільний резерв вичерпаний, нові UID не спричиняють записів D1 чи читань Firebase. Відомий ключ визначає тільки квоту; актуальні права, блокування й відкликання завжди перевіряються у Firebase. Неправильні ключі не запускають читання Firebase.
- Queue обробляє по 5 записів, один consumer. Повторює тимчасову помилку до 3 разів з паузою 60 секунд. D1 outbox відновлює втрату відправлення кожні 5 хвилин. Приватна Firestore квитанція забезпечує відновлення після неоднозначного commit.
- Вичерпання ліміту Queue залишає JSON у D1 до наступної доби. Через 24 години незавершений job переходить у failed. Payload очищається у terminal state; історія/receipt очищаються після 30 днів.
- Очищення історії має окремий резерв 200 спроб/UTC день. Протерміновані ключі, інтервали та старі персональні лічильники очищаються обмеженими порціями раз на добу. При 450 MiB D1 нові імпорти й створення нового ключа призупиняються; читання, видалення та ротація наявного ключа залишаються доступними в межах квот.
- Стани: queued / processing / completed / partial / failed / cancelled. Перевіряйте статус не частіше ніж раз на 30 секунд і припиніть polling після terminal state. Перевірка статусу теж витрачає денну квоту.
- HTTP-помилки повертаються як `{"error":{"code":"HTTP_429","message":"…"}}`. 401 — ключ/сесія; 403 — права; 409 — idempotency; 413 — розмір; 415 — Content-Type; 422 — JSON або структура запиту; 429 — квота з Retry-After; 503 — недоступність сервісу. Після 202 помилки перевірки полів повертаються через `error` стану імпорту з кодом HTTP_422. Після успішної перевірки JSON помилки обробки окремих позицій повертаються у results, інші позиції можуть бути застосовані.
- OAuth-токен службового акаунта оновлюється лише consumer черги й зберігається у D1 зашифрованим AES-GCM. HTTP не виконує RSA minting: до початкового прогріву або при недоступному токені повертає 503 з `Retry-After: 60`. Службовий Cron надсилає повідомлення кожні 5 хвилин; після релізу перевірте його успішне виконання перед прийманням API.

Великий імпорт не є однією транзакцією. Зміни ролі/ключа чи збій можуть залишити вже оброблену частину. Якщо неможливо прочитати квитанцію останньої порції, job явно попереджає про можливий запис. Звірте каталог і results перед новим імпортом; незмінний externalId запобігає створенню нового дубліката.

## Відтворення інфраструктури та повторний реліз

Нижче інструкція відновлення/наступного релізу, а не список ще не виконаних команд: поточну інфраструктуру вже активовано. Не створювати зайві service-account keys або Queue, не повторювати міграції вручну й не послаблювати Rules. Firestore enforcement вимагає сумісного клієнта App Check; старий реліз без SDK не є безпечним автоматичним rollback. [Поточна конфігурація захисту](./FIREBASE_SECURITY_ACTIVATION.md).

Новий consumer підтримує попередні нормалізовані завдання та нові завдання з префіксом `raw:` у `payload_hash`. Старі версії Worker не обробляють новий формат: перед поверненням до старого consumer дочекайтеся завершення всіх активних `raw:` завдань або використайте сумісну виправлену версію. Міграція схеми для цього формату не потрібна.

1. У Firebase/Google Cloud проєкті **kilo-g**, акаунтом його власника, створити окремий service account `kilog-import-worker`. Надати **Cloud Datastore User** (`roles/datastore.user`) для транзакцій Firestore та **Firebase Authentication Viewer** (`roles/firebaseauth.viewer`) для перевірки enabled/emailVerified/revocation. Створити JSON key; зберігати поза репозиторієм у каталозі з ACL лише власника. Не використовувати особистий refresh token, Firebase web API key чи VITE_*.
2. OAuth цього service account використовує IAM і обходить Firestore Rules. Саме Worker повторно перевіряє поточний акаунт, роль, memberships, блокування, accountDeletion, компанію, домен і blocked status у кожній порції. Rules не послаблюються; нова приватна collection importReceipts залишається недоступною клієнтам.
3. Створити Queue `npx wrangler queues create kilog-imports --message-retention-period-secs 86400`. Залишити max_concurrency=1, max_batch_size=1, max_retries=3; не підключати стороннього consumer.
4. Зберегти резервну копію D1, потім `npx wrangler d1 migrations apply kilog-analytics --remote`. Міграція 0002 додає import_* tables/triggers/indexes; 0003 додає окремий бюджет адміністратора й персональні лічильники. Каталог Firestore не переміщується.
5. Підготувати захищений secrets JSON поза Git: поле `FIREBASE_IMPORT_SERVICE_ACCOUNT` зі **string**, який містить увесь JSON service account. Не друкувати значення в терміналі/логах. Існуючий TURNSTILE_SECRET_KEY не видаляється: secrets-file застосовується додатково.
6. `npm run lint`, `npm test`, `npm run test:emulators`, `npm run build`, `npx tsx scripts/deploy-validation.ts`, `npx wrangler deploy --dry-run`. Лише після дозволу — `npx wrangler deploy --secrets-file <захищений-файл>`. Не використовувати secret put як окремий передчасний реліз.
7. На окремій тестовій компанії виконати контрольоване admin/manager приймання, перевірити Auto company, denied foreign URL, rotation/revoke, Queue/crons, журнал і фактичний billed CPU. Відрізняти виконані live admin checks від локальних manager regressions; не оголошувати всю live матрицю завершеною без відповідного приймання.

Для аварійного повного відключення імпорту спочатку зупинити consumer Queue й відкликати IAM-доступ service account. Відкат Worker обирати за [OPERATIONS.md](./OPERATIONS.md): попередня версія `d7f4f6aa-e18e-45d0-9365-f7296f5de87d`, source `9f2d8ba`, сумісна з App Check/CSP, але повертає автоматичну публікацію імпорту та окрему сторінку компанії. Вона не зберігає новий контракт чернеток. Старий клієнт без SDK не працюватиме з чинним Firestore enforcement. D1 import_* таблиці залишити для розбору/відновлення. Уже записані Firestore пропозиції не видаляти автоматично. Видалення ключа service account припиняє minting нових токенів; для негайного відключення потрібне відкликання IAM-доступу, оскільки виданий OAuth token може ще діяти.

## Видалення історії

У кабінеті можна видалити один запис або обрані завершені імпорти після підтвердження. Менеджер керує лише власною історією, адміністратор — усією. Імпорти `queued`/`processing` та скасовані завдання з активною порцією Queue не видаляються. Товари, компанії, API-ключ, інтервал і витрачені квоти збережені.

Обидва DELETE endpoints приймають чинний API-ключ або поточну сесію кабінету з App Check. Права перевіряються свіжо. Відповідь 200 містить `deletedIds` та `unavailableIds`; чужий, відсутній або ще активний ID не розкриває причини відмови. Повторне видалення власного вже прибраного запису ідемпотентне. Некоректний JSON/ID, дублікати, порожній або завеликий список дають 422; понад 4 KiB — 413. Спільний резерв ручного та автоматичного очищення — 200 ID-спроб на UTC-добу; недоступні й повторні ID також рахуються. При нестачі резерву весь запит відхиляється з 429/Retry-After.

Після видалення GET не повертає запис і його результати. Службовий рядок та receipt залишаються до фонового очищення, щоб запізнілий повтор не створив дубль. Після 30 днів запис доступний для фізичного очищення; спільний добовий резерв може відкласти його. POST зі старим `Idempotency-Key` повертає 409; для нового імпорту використовуйте новий ключ запиту. Повернути видалену історію через кабінет неможливо. Міграція `0011_import_history_delete.sql` додає прапорець та часткові індекси видимої історії; дані не видаляє і не змінює статуси товарів.

## Межі безкоштовного плану

За [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/) Free має 10 000 операцій/день. Наші 500 імпортних + 300 службових повідомлень, до 3 retries і перенесення попередньої UTC-доби дають консервативну модель 9600 операцій: `2 × 800 writes + 2 × 800 × (4 reads + 1 delete)`. Записи резервуються також для попередньої доби, якщо відправлення затрималося через межу UTC. Повідомлення містить тільки короткий покажчик; JSON залишається в D1. Це модель трафіку застосунку, а не тверда межа обліку акаунта: затримки відправлення через кілька UTC-діб, інші Queue та ручні відправлення поза резервом потребують окремого бюджету. [Free retention](https://developers.cloudflare.com/queues/platform/limits/) — 24 години після відправлення; строк виконання job окремо обмежений 24 годинами після створення. [Workers Free](https://developers.cloudflare.com/workers/platform/limits/) має 10 мс CPU для HTTP; consumer черги має окремий більший бюджет. Локальні тести не вимірюють production billed CPU. [Firebase REST](https://firebase.google.com/docs/firestore/use-rest-api) описує різницю між Rules та IAM.

Актуальні вимірювання CPU, контрольні навантаження й версія релізу наведені у [WORKER_LIMITS.md](./WORKER_LIMITS.md). Старий source `9f2d8ba` мав P99 до 21.670 мс; це історична вибірка, а не приймання чинної версії. Startup time не вимірює CPU запиту.

Ліміти обмежують витрати, але інші функції сайту використовують ті самі ресурси Firebase. Безкоштовний план не гарантує необмежене навантаження або 100% доступність. При квоті/недоступності API закриває доступ чи відкладає job замість неконтрольованих записів.
